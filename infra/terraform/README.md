## Layout

```
infra/terraform/
  modules/            network, ecs_service, rds, redis, s3, kms, secrets, alb_waf, observability
  envs/dev|staging|prod/
    backend.tf        S3 state + DynamoDB lock (partial config: bucket and table names are not in the repo)
    variables.tf      sizing defaults for that environment (the only intentional difference between envs)
    main.tf           wires the modules (identical in all three envs)
    github_actions.tf OIDC provider + deploy role (identical)
    outputs.tf        (identical)
    terraform.tfvars.example   non-secret inputs you must fill
infra/scripts/        bootstrap-state.sh, compose-database-url.sh, ecs-*.sh, smoke-test.sh, k6_light.js
.github/workflows/    deploy-dev.yml, deploy-staging.yml, deploy-prod.yml
```

`main.tf`, `versions.tf`, `github_actions.tf` and `outputs.tf` are copies. Edit one, copy to the others, and run
`infra/scripts/check-env-parity.sh` to catch drift. Module names are provider-neutral (`network`, `rds`,
`redis`, `s3`, `kms`, `secrets`, `alb_waf`) so a GCP Johannesburg port stays possible; the module internals are AWS.

## Variables you must provide

Per environment (`terraform.tfvars`, no secrets; copy from `terraform.tfvars.example`):

- `domain`: base domain. Hosts become `api.<domain>`, `admin.<domain>`, `pay.<domain>`.
- `certificate_arn`: an ACM certificate in the same region covering those three hosts. Not created here.
- `github_repository`: `ORG/REPO`.
- `admin_ip_allowlist`: required (non-empty) in staging and prod.
- `app_extra_environment`: non-secret provider settings. `staging.py` and `prod.py` require real values for
  `SMS_PROVIDER`, `IDENTITY_PROVIDER`, `MALWARE_SCANNER`, `PUSH_PROVIDER`, `PAYMENT_GATEWAY`, `EMAIL_PROVIDER`,
  `STAFF_SSO_PROVIDER` (and prod also `IMAGE_MODERATION_PROVIDER`). Dotted paths of the classes that exist in
  `backend/mc/*/providers/` are in the example file. Pick them deliberately.
- `region` defaults to `af-south-1`. Data residency is PENDING OD-04; change the default only after that decision.

Backend (state) configuration, passed at `terraform init`: `bucket`, `dynamodb_table`, `region`.

## Order of operations

1. Create or choose the AWS account(s). One account per environment is recommended. If dev, staging and prod
   share an account, only one environment may set `create_github_oidc_provider = true` (dev does by default;
   the others look it up), so apply dev first.
2. Bootstrap state once per account:
   `AWS_REGION=af-south-1 infra/scripts/bootstrap-state.sh <state-bucket> <lock-table>`
3. Request and validate an ACM certificate for `api.`, `admin.`, `pay.<domain>` in the region.
4. For an environment: `cd infra/terraform/envs/<env>`, copy `terraform.tfvars.example` to `terraform.tfvars`, fill it,
   then
   `terraform init -backend-config=bucket=<b> -backend-config=dynamodb_table=<t> -backend-config=region=<r>`,
   `terraform plan`, review, `terraform apply`. Commit `.terraform.lock.hcl`.
5. Create DNS records for `api.`, `admin.`, `pay.<domain>` pointing at the `alb_dns_name` output (DNS is not managed
   here because the registrar is undecided).
6. Populate secrets out of band. For each name in the `secret_arns` output:
   `aws secretsmanager put-secret-value --secret-id mc/<env>/<NAME> --secret-string file://...` (read values from your
   password manager, never commit them). `DATABASE_URL` is composed from the RDS-managed credentials with
   `infra/scripts/compose-database-url.sh <env>`. It uses the RDS master user: create a least-privilege application
   role and rotate before real users (follow-up).
7. In GitHub, create the environments `dev`, `staging`, `production`. In each set variables `AWS_DEPLOY_ROLE_ARN`
   (the `github_deploy_role_arn` output), `MC_DOMAIN`, optional `AWS_REGION`. On `production`, add required
   reviewers: that is the manual approval gate for `deploy-prod`.
8. Trigger the first deploy (push to main for dev, tag `rc-*`, tag `v*`). Until an image exists the services cannot start
   (the Terraform task definitions point at the tag `bootstrap`), so expect failing tasks and alarms before the first
   successful deploy.
9. Staging/prod: tune WAF (`waf_managed_rules_count_only = true` first if legitimate traffic is blocked), add
   `alert_emails` or subscribe on-call tooling to the SNS topic.

## Deploy flow

- Terraform owns infrastructure and the initial task definitions. The ECS services ignore later changes to
  `task_definition` and `desired_count`; the workflows register a new revision cloned from the family's latest revision
  (so Terraform config changes are kept) with only the image replaced, then update the service.
  Do not run `terraform apply` expecting it to roll the image back or forward.
- `deploy-dev`: main push, build `backend/Dockerfile`, push ECR (immutable tag = first 12 chars of the commit SHA), run
  the migrate task, rolling deploy, smoke test.
- `deploy-staging`: same on tag `rc-*` (must be on main), plus `infra/scripts/k6_light.js`. The 2,000-socket chat test
  in `loadtests/ws_chat.js` is not run by the workflow (it needs seeded tokens).
- `deploy-prod`: tag `v*` (semver, on main) -> approval on the `production` environment -> build -> pre-migration RDS
  snapshot (`mc-prod-premigrate-<run>-<sha>`, waits until available) -> migrate -> rolling deploy ->
  smoke test of `https://api.<domain>/ready` -> automatic rollback to the previous task definitions if the rollout does not
  complete or the smoke test fails. Rollback reverts the app only. Migrations must follow expand, migrate, contract
  (Bible 13.3) so the previous release still works on the new schema. Restoring the snapshot is a manual runbook step.
- Manual snapshots are not deleted automatically; clean them up periodically.

## NOT verified / known gaps

1. Nothing was applied or validated against AWS (see top). Provider argument names and versions (`~> 5.70`) are
   from memory.
2. ALB health checks carry the target IP as Host; the backend now serves `/ready` and `/health` for any host (probe paths only), so the matcher is a strict `200`.
3. Not provisioned: ClamAV/clamd (`MALWARE_SCANNER`, `CLAMD_HOST` need a service; Bible 3.2 has it locally), SES identities
   and DKIM, Route 53/ACM, FCM/Play/Apple credentials (only the secret slots exist), CloudFront in front of `static-public`.
4. Redis has TLS and security-group isolation but no AUTH token. `REDIS_URL` is `rediss://...?ssl_cert_reqs=required`;
   confirm Celery and Channels accept it as configured.
5. `DATABASE_URL` uses the RDS master user (see step 6). `MC_DATA_KEYS_JSON` holds wrapped data keys; how the app unwraps
   them with `mc-data` is not defined in settings, so the task role simply has encrypt/decrypt on the key.
6. Every service receives every secret, for simplicity; split per service for least privilege later. The task role grants
   `rekognition:DetectModerationLabels`; check Rekognition availability in af-south-1 before relying on it.
7. SNS topic and WAF/CloudWatch log groups use service-default encryption, not `mc-data`. Enhanced RDS monitoring and cross-region backup
   copies are not configured.
8. Each environment has its own ECR repository and rebuilds from the tag, so staging and prod images are not the same digest.
   Promotion by digest would be stronger.
9. GitHub Actions are pinned by major version, not by commit SHA. The OIDC thumbprint is a placeholder that AWS ignores for GitHub.
10. WAF rule tuning (CommonRuleSet body-size and similar rules) is untested against real mobile traffic. The auth rate-limit path
    prefix `/api/v1/auth` is an assumption; adjust `auth_path_prefix` to the real OTP routes.
11. The restore drill required by MC-124 (restore evidence from a snapshot and from PITR) has not been done. Runbooks exist in `docs/runbooks/` but have never been exercised by a game-day.
12. Sizing numbers are starting guesses; no load test informed them.

13. The alarms added for Bible §15 (`alb_p95_latency`, and the `queue_age_high`, `payment_webhook_failures`, `otp_send_spike`
    metric filters/alarms) were written but NEVER planned or applied (no AWS access or registry here); `terraform fmt` and the
    env-parity script are the only checks run. The metric filters depend on the application emitting those JSON `alert`
    lines (covered by backend unit tests). `METRICS_TOKEN` is a new empty Secrets Manager entry: an operator must set a value,
    otherwise `/metrics` stays disabled (403). To enable tracing set `OTEL_EXPORTER_OTLP_ENDPOINT` via `app_extra_environment`.
