# Open questions raised during the build

Per CLAUDE.md §6 these are `QUESTION:` items found while implementing; each uses the smallest safe
behaviour until answered. Update this file (and the Bible) when a decision lands.

| # | Area | Question | Current behaviour |
| --- | --- | --- | --- |
| Q1 | Special data in ranking | CLAUDE.md rule 4 says special data (religion, money attitudes) is NEVER used in ranking; Bible §10.6 allows "the faith-match answer the user chose to answer". | Faith answers (`faith_practice`, `faith_importance_in_partner`) are `scoring_allowed=true`; money attitude is `false`. Flip `Question.scoring_allowed` (or reseed) to exclude faith too. |
| Q2 | Married-status gating | Bible §7.3 names only the declaration; `married_visibility` consent kind exists. | Married status and opting in to see married profiles both require the `married_visibility` consent as well as the declaration. Withdrawing it hides married profiles from the user's discovery. |
| Q3 | Verification submitted state | Bible §10.2 has a `submitted` state but §8.2 has no endpoint to enter it. | Added `POST /verification/sessions/{id}/submitted` (idempotent; starts the polling-fallback clock). |
| Q4 | Device identity | §7.1 `Device` has no per-install identifier, needed for "new device" detection. | Added client-generated `install_id` (UUID) with unique(account, install_id). |
| Q5 | Idempotency as middleware | MC-013 says middleware; the account is only known after DRF auth. | Implemented as a DRF view mixin (`IdempotentMixin`) with the same semantics. |
| Q6 | PostGIS | §7.3 `geography(Point)`. | Deferred; rounded lat/lng columns (ADR-0002). |
| Q7 | Questionnaire content | ~25 core questions "from product team". | Draft placeholder set in `mc/questionnaire/fixtures/questions_v1.json` — needs product/UX review, Luganda/Swahili copy, and scoring-matrix review. |
| Q8 | Consent erasure | Consent rows are append-only, but account hard-delete must remove them (or retain as evidence?). | Deleted with the account via an explicit DB escape hatch; counsel to confirm retention (MC-004). |
| Q9 | Smile ID adapter | Written from public docs, unverified against the sandbox. | Fake provider used everywhere; real adapter flagged until MC-030. |
| Q10 | Deal-breakers | §7.3 `Preference.dealbreakers` duplicates `Answer.is_dealbreaker`. | Single source of truth is `Answer.is_dealbreaker`; `Preference` omits the column. |
| Q11 | Profile visibility endpoints | §8.2 has no go-live / hide endpoints. | Added `POST /me/profile/go-live`, `/hide`, `/unhide`; a live profile auto-drops to draft if go-live rules stop holding. |
| Q12 | Public identifiers | Interest/discovery examples use `recipient_id` / `sender.id` without saying whether account or profile ids. | The public handle everywhere between members is the **profile id**; account ids and phone numbers never reach other members. Media object keys contain no account id either. |
| Q13 | After unmatch | §10.5 says a match never re-activates but not whether the pair can re-match. | Unmatched pairs are hidden from each other and blocked from re-sending interests for `INTEREST_RESEND_COOLDOWN_DAYS` (90). |
| Q14 | Staff identity | Moderation/enforcement/appeal services take a `staff` id + role, but `StaffUser`, SSO and MFA arrive with the admin portal (MC-113). | Services accept a staff UUID and role string and audit them; the portal will supply real StaffUser ids and enforce the role matrix (§12.4). Until then these services are not reachable over HTTP. |
| Q15 | s2/s3 SLAs | Planning package gives s1 = 1 h and s4 = 5 d only. | s2 = 4 h, s3 = 24 h (config `SAFETY_SLA_HOURS`). |
| Q16 | Suspended members | Not specified what a suspended member may do. | They can sign in (OTP) to see the decision and appeal, plus account controls (sessions, consents, devices, notifications); every member feature returns 403, and sockets are refused. |
| Q17 | Deleted member's chat | §10.9 says their sent messages become "message deleted" placeholders in the other member's history, but a closed match is hidden from the other member anyway. | Matches are closed (hidden) at deactivation; at hard delete the Match rows and their messages are removed with the account (sent messages are first scrubbed to placeholders). Reports keep their own evidence copy. |
| Q18 | Re-registration after deletion | Retained verification decision + "one identity → one account". | The identity uniqueness only binds *live* accounts (a deleted account frees its ID), but the one-trial-per-person rule survives via the retained hash, and banned identities stay banned. |
| Q19 | Reinstating a deactivated account | §10.9 gives no member-side undo. | Inside the grace period only support/privacy officer can cancel (audited); the member cannot sign in while deactivated. |
| Q20 | Pay-host sign-in | §11.3 says "phone OTP login (same accounts)" but not whether new numbers may register there. | Members only: an unknown number gets the same page but no SMS and no account is created (no enumeration). |
| Q21 | Web receipts | §11.3 asks for receipts by SMS/email; neither template/consent is specified. | On-screen receipt only (reference, period, amount). SMS/email receipts wait for counsel on consent wording. |
| Q22 | Staff break-glass | §12.4 mentions superadmin dual-approval break-glass. | Not built: superadmin grants nothing by itself beyond `config.flags` / `staff.manage`; raise a ticket before building it. |
| Q23 | Support notes | MC-114 asks for "notes" without a retention rule. | Append-only, field-encrypted, erased with the account, no chat or special data allowed (form says so). |
| Q24 | Mobile consent guard | A user who signs in but quits before consents lands on Home on restart. | Backend still refuses verification without the three required consents; a server-driven guard (`/me`) is planned with MC-040. |
| Q25 | iOS flavors/schemes | Need macOS/Xcode. | Android flavors done; iOS schemes deferred (documented in apps/mobile/README.md). |
| Q26 | Store-review demo login | `seed_demo` only runs under local/dev/test settings and prod has no fixed OTP, so store reviewers have no login (MC-125). | BUILT: `REVIEW_ACCOUNT_PHONE`/`REVIEW_ACCOUNT_CODE` (secrets store) enable one fixed-code reviewer sign-in (rate limited, audited, no SMS); `manage.py create_review_account --confirm` provisions it with 60 days of membership. Disabled when unset. |
| Q27 | Public account-deletion page | Google Play requires a web path to request deletion in addition to in-app `DELETE /me`. | BUILT: public `/delete-account` page on the pay host (the Data Safety URL); deletion itself still needs the in-app re-auth code. Support mailbox address is a placeholder (`SUPPORT_EMAIL`). |
| Q28 | Rekognition in af-south-1 | Moderation adapter defaults `AWS_REGION=af-south-1`; availability of Rekognition there is unconfirmed. | `MODERATION_AWS_REGION` now overrides the region for Rekognition only. Verify availability before the MC-061 test; if unsupported choose another region with counsel's approval. See docs/vendor-evaluation/moderation.md. |
| Q29 | OTP spike alert has no runbook | Bible 15 alerts on OTP send spikes (SMS pumping) but `docs/runbooks/` has no matching runbook. | BUILT: `otp_send_spike` alert (`OTP_SPIKE_ALERT_PER_HOUR`) and docs/runbooks/otp-spike.md. |
| Q30 | Store payment viability in Uganda | MC-001 research (docs/adr/0007-billing.md) found no evidence that Uganda is eligible for Google user-choice billing/external offers or Apple link-out, and could not confirm which store payment methods (cards, carrier billing, gift cards) work for Ugandan accounts. If store payment is impractical, the "never mention web checkout" rule leaves members with no in-app route to the working channel. | No code change. Keep two channels and the no-web-mention rule; human checklist in the ADR; product/counsel to decide on compliant off-app messaging before M8. |
| Q31 | Hosting region and Rekognition | OD-04 brief (docs/adr/0008-hosting-region.md): Rekognition appears absent from af-south-1 (unconfirmed; extends Q28) and sources disagree whether DPPA s.19 requires adequacy AND consent or either. | Default stays af-south-1; Rekognition region override only after a live API check and counsel approval. |
| Q32 | PDPO fee and DPO rules | Sources conflict on the registration fee (UGX 100,000 vs 200,000) and on the regulation citing the duty; DPO appointment rule not confirmed from primary text (docs/prelaunch/pdpo-registration.md). | Nothing filed; human to confirm on the PDPO portal and with counsel. |
| Q33 | TwilioSms fallback missing | Bible 11.4 names `TwilioSms` as the fallback SMS provider, but only `AfricasTalkingSms` and `FakeSms` exist; the Africa's Talking adapter also hard-codes the live URL (no sandbox host). Sender ID registration for Uganda is reported as required (docs/prelaunch/sms-sender-id.md). | Only Africa's Talking is implemented; leave `AT_SENDER_ID` empty until a sender ID is approved. A ticket is needed for a second provider or sandbox URL setting. |
| Q30 | Dashboard permissions | Bible §15 lists the admin dashboards but §12.4 has no column saying who may open them. | New permissions in `adminportal/policies.py`: `dashboard.funnel` (conversion) -> payments_ops, privacy_officer; `dashboard.density` -> trust_safety, privacy_officer; `payments.reconciliation` -> payments_ops, privacy_officer. Verification and moderation queues keep `verification.queue` / `safety.queue`. engineer_oncall stays "no production data" and superadmin grants nothing by itself (Q22). Both dashboards are aggregate-only and hide any cell under `AGGREGATE_MIN_CELL` (5); complementary suppression is not applied, so a total derived from two different pages could still reveal a single hidden cell to someone who may open both. |
| Q31 | Verification review SLA | Planning package gives SLAs for safety cases only (Q15), not for manual verification review. | `VERIFICATION_REVIEW_SLA_HOURS = 24` (A): a review is due 24 h after the attempt was created (`needs_review` has no timestamp of its own). Derived for the queue page, not stored. |
| Q32 | Runtime feature flags | Bible §17 allows "django-waffle or a small table + cache". Phase 5 flags exist but CLAUDE.md rule 12 forbids building those features. | Small table (`mc.flags.FeatureFlag`) + 30 s Redis cache that degrades to `FEATURE_FLAGS_DEFAULT`. The three `phase5_*` flags are locked off: they read as off even if a row says on, and `set_flag` refuses to enable them until a backlog epic removes the lock. `ranking_model_vN` is accepted for any N (default key `ranking_model_v2`, off); nothing reads it yet. `GET /config/flags` (public, allowlist `voice_notes`, `data_saver_default_on_cellular`) is new; the app's `GET /config` for product values from §17 is still unbuilt. A reason is mandatory on every change. |
| Q33 | Bible §8.2 unblock path | §8.2 lists `DELETE /blocks/{account_id}` but members only ever see profile ids (Q12, CLAUDE.md rule 3). | The API is `DELETE /blocks/{profile_id}` and `POST /blocks` takes `profile_id`; §8.2 corrected. Also added to §8.2: `GET /me/devices`, `GET /config/flags`. |
| Q34 | Funnel and reconciliation definitions | §15 names the funnel stages but not the counting rules; the nightly reconciliation report was only logged. | Funnel is a cohort by registration date (Kampala days, max 366): of accounts registered in the range, how many have a passed verification, a live (or member-paused) profile, sent an interest, are in a match (any status), and hold an un-refunded purchase-backed entitlement (trials and staff grants excluded). Deleted accounts are not counted. The nightly report is now persisted (`billing.ReconciliationReport`, 90 nights, mismatch list capped at 500) so the portal can show it; the page warns when no run happened for 36 h. |
| Q35 | Push payload shape | Bible §11.4 says data-only FCM messages, but the backend sends a `notification` block plus data. | Kept as is: the OS shows our generic text while backgrounded without needing local-notification code in the app. Revisit if foreground banners are wanted. |
| Q36 | Discovery and answer caches in Redis | Performance work caches per-account non-special questionnaire answers (15 min) and the first-page scored pool (60 s) in Redis under opaque keys. | Never caches special-category answers; switchable off (`QUESTIONNAIRE_SCORING_CACHE_SECONDS=0`, `DISCOVERY_SNAPSHOT_REUSE_SECONDS=0`); counsel to confirm. A candidate who withdraws special-category consent can still appear in a viewer's cached pool for up to 60 s. |
| Q37 | Process model | Bible §2.2 says REST runs on `gunicorn config.asgi` / Uvicorn. Under ASGI every sync view runs on a single thread per worker (measured by the load test). | REST now runs on `gunicorn config.wsgi --worker-class gthread`; WebSockets stay on ASGI (uvicorn). Daphne is dev-only because of an unfixed Twisted CVE. |
| Q38 | Review-account lockout | The store-review fixed-code login has one global attempt limit, so anyone who knows the review phone number could lock reviewers out. | Accepted for now (number is not public); move to per-IP buckets if it is ever exposed. |
| Q39 | Mobile refresh policy | Bible §5.4 says "log out on failure" of a token refresh. | The app signs out only on a definitive 4xx; offline, timeouts and 5xx keep the session. |
| Q40 | Dashboards differencing | Funnel ranges could be subtracted to isolate a single day below the small-cell threshold. | Ranges snap to whole Mon-Sun weeks. |
| Q41 | v2 "About you" before verification | user-flow-v2 §2 row 4 collects first name, birth date and gender before the ID check, but the Bible stored a profile only for verified adults and §4 names no endpoint. | `PATCH /me/profile` creates the draft for an unverified member from a declared `birth_date` (18+, else `underage` without suspension). The passed verification's date of birth replaces it and locks it (also adopted on `AccountVerified`). Photos, descriptions, answers and go-live still need verification. |
| Q42 | Marital status in the short go-live | v2 row 8 omits marital status, but BR-MAR-01 / OD-03 filters married profiles on it. | Marital status stays required for go-live (timeline became optional) so a married member cannot hide it. Product/counsel to confirm; relaxing it needs an alternative way to keep married profiles opt-in. |
| Q43 | Quota semantics | v2 gives "3 / rolling 7 days" without saying what counts. | Every interest the account created in the window counts (including ones sent during a trial, passed, expired or cancelled); replays and send-back-accepts cost nothing; trial/member are exempt. Expired accounts therefore start with the sends of their last 7 days. |
| Q44 | Capability flags without behaviour | v2 lists priority placement, extra filters and a higher interest cap as member perks, but §10.6 forbids payment status in ranking and no extra filters exist. | `priority_placement` / `extra_filters` are capability flags only (nothing reads them); `higher_interest_cap` is the daily cap for trial/member. Needs a product decision before any ranking change. |
| Q45 | Funnel events live in `accounts` | A new `mc/<module>` needs a pyproject import-linter contract. | `FunnelEvent` is stored in `mc.accounts` (no account FK; HMAC of install/account id; one row per actor and step; 400-day retention). Move it to its own module if analytics grows. |
| Q46 | Anonymous funnel identity | Anonymous clients are identified only by a client-generated install id. | Stored as `HMAC(account pepper, "funnel|install|<id>")`; a client can inflate counts by generating ids, bounded by per-IP and per-actor rate limits. Counts are indicative, not audited. |
